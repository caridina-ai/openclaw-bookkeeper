## 第一章　具有固定格式，可由 script 直接處理的輸入詞

| 格式 | 範例 | 備註 |
|---|---|---|
| `{item}{number}` | 冰茶40、水果509、理髮130、牙間刷447、某牙醫2250、手機機車架790、開水壺1099、義大利麵195 | 最大宗。中間空白可有可無；全形數字先轉半形。**須呼叫 AI 判科目**（附錄 A‑1） |
| `{item}{number} {科目}` | 維他命飲67 外食費、油漆刷30 居住費、滑鼠墊60 精進金 | 尾端直接命中 `categories` 表 → **不必呼叫 AI** |
| `{item}{number} 記在{科目}` | 伴手禮1050 記在公關費、菊花茶15 記在 公關費 | 與上一列同一個 parser：尾巴的 `記在\|歸在\|算\|列在\|放` 視為贅詞 |
| `{item}{number}` × N 行 | 開水壺1099⏎榨果汁器550⏎運動水壺499、毛巾79⏎毛巾59⏎毛巾98、油漆刷15⏎油漆刷30 居住費⏎滑鼠墊60 精進金 | 逐行套用上面三列，依序輸出多行 stdout。同一則訊息可混用有／無科目 |
| `提款{number}` | 提款3000、提款5000、提款2000 | 關鍵字表 → `in`：提款、提領、領錢、ATM、入金、薪水、酬勞、退款、中獎、撿到。note 保留完整前綴（`某銀行提款2000`）。**例外**：含「手續費」者是支出 |
| `{item}後{number}`／`{item}完{number}` | 買菜後3229、買菜完1263 | 倒推 → `out --balance`。仍**須呼叫 AI 判科目** |
| `{item}{number} {date}{time}` | 豆包55 記在 8/5 18:00、買豆包後2253，記在昨天 18:00 | date：`M/D`、`YYYY-MM-DD`、今天／昨天／前天／大前天；time：`HH:MM`。**日期時間換算不必呼叫 AI**（附錄 A‑2） |
| `{date}{time} {item}{number}` | 昨天18:00 自助餐120、19:30 理髮150 | 頻道裡沒出現過這個順序，但同一支 parser 頭尾都掃就同時支援 |
| 餘額查詢 | 餘額多少、餘額多少？、顯示餘額 | `^(顯示\|查\|現在\|目前)?\s*(餘額\|剩多少\|還剩多少)[多少嗎呢？?\s]*$` → `balance`。**不必 AI** |
| `{期間}{報表名}` | 七月分類帳、七月分類統計、七月分類明細、七月分帳明細、七月依科目明細 | 報表名是固定同義詞表（SKILL.md 已有四組）；期間支援 七月／8月／2026-07／7/8／今天。**必須 longest‑match**：先比「分類明細／分帳明細／依科目明細」，再比「分類帳／分類統計」，否則 `七月分類明細` 會被 `分類` 先吃掉。**不必 AI** |
| 說明 | 說明 | 說明、幫助、help、怎麼用、有哪些功能 → `guide`。**不必 AI** |
| 科目管理 | 列出所有科目、新增科目X、刪除科目X、把X更名為Y、刪除全部科目 | 頻道裡只出現過口語版（見第二章），但這組關鍵字格式固定，值得先做。**不必 AI** |
| `展開{科目}[、{科目}]` | 展開交通費和保健費 | 科目名直接跟 `categories` 表比對。**不必 AI** |

### 關於「彈性 parser」——妳問的那一題

**做得到，建議做。** 結構是「核心 ＋ 尾巴」：

```
核心： {item}{number}          ← 必要，用貪婪數字結尾抓
尾巴： 剩下的字元              ← 可有可無
```

尾巴丟進一個小掃描器，只認三種東西：**科目名**（比對 `categories` 表）、
**日期／時間字面值**、以及一份**贅詞白名單**：

```
時間、是、在、幫我、記、記在、記做、改在、歸、歸在、算、列在、放、的、了、好、，、,
```

尾巴全部被這三類吃光 → 處理掉；**剩下任何一個白名單外的詞 → `exit 20` 交給 AI**。
所以下面這些會走同一條路：

```
理髮150 19:30
理髮150 時間是19:30
理髮150 時間幫我記在19:30
豆包55 記在 8/5 18:00
伴手禮1050 記在公關費
```

這個設計的好處是**保守**：白名單沒收錄的講法會自動退回給 AI，不會誤記。
白名單日後隨 log 慢慢加，是純加法、不會回歸。

## 附錄 A　script 裡須要呼叫 AI 的函數

### A‑1　`品項 → 科目`（唯一必要的一個，妳的判斷正確）

```
classify(note: string, categories: string[]) -> string | null
```

`自助餐 → 外食費`、`理髮 → 治裝費`、`牙間刷 → 保健費`、`滑鼠墊 → 精進金`。
只有這件事沒有確定性解法。

**強烈建議加一層學習型快取**（`item_category` 表，命中就完全不呼叫 AI）：

現有帳本 69 筆支出、39 個相異品項，**43.5% 的寫入是重複品項**——
`冰茶`×12、`外食`×6、`買菜`×4、`水果`×4、`某牙醫`×3、`毛巾`×3、
`拉麵店`×2、`晚餐`×2、`油漆刷`×2、`奉獻`×2。
使用愈久命中率愈高，AI 呼叫會收斂到「這輩子第一次買的東西」。

快取寫入時機有三個，都不必額外呼叫 AI：
1. AI 判過一次之後寫入；
2. 使用者明講科目（`維他命飲67 外食費`）→ 直接寫入，這是最可靠的訓練資料；
3. 使用者事後糾正（`不是雜費，這三筆毛巾都記在 居住費`）→ 覆寫。

呼叫方式當時建議由 plugin 代打。問題要窄到一行：
「品項『X』屬於下列哪一個科目？只回科目名。」

> **後記（階段二實作時修正）**：plugin 不需要代打，也不該代打。script 自己跑
> `openclaw infer model run --gateway --json` 就有，而且不指定 `--model` 時
> 吃的是 `agents.defaults.model` 的 primary + fallbacks，備援照樣生效。
> 詳見 chat-interceptor 的 AUTHORING.md 第 8 節。

**判不出來時不要硬塞雜費**——舊 SKILL.md 最後一行就是這麼要求的，
`classify` 回 `null` 時應該 `exit 20` 讓 AI 接手問使用者。

### A‑2　日期時間：確認妳的判斷——**不必呼叫 AI**

`昨天18:00`、`19:30`、`8/5 18:00`、`前天`、`7/8` 全都是純字面值換算，
用 script 的當下時間當基準即可，零歧義。這條不需要模型。

### A‑3　我在整理過程中另外檢查過、結論是「也不必 AI」的幾項

| 看起來像要 AI 的地方 | 為什麼不用 |
|---|---|
| 入金 vs 支出 | 固定關鍵字表（提款/提領/薪水/酬勞/退款/中獎/撿到），加一條「含手續費 → 支出」的例外 |
| 倒推時抽品項 | `買菜後3229` 去掉 `後{number}` 就是品項，純字串操作 |
| 報表同義詞（分帳／分類帳／科目統計…） | SKILL.md 已經是固定四組對照表，查表即可 |
| 科目名講得模糊（`「不予計算」還是「不統計」`） | 拿 `categories` 表做子字串／編輯距離比對；比不到就 `exit 20`，不要猜 |
| 期間換算（七月／8月／今天） | 同 A‑2，字面值換算 |

### A‑4　唯一的第二候選（建議先不做）

「批次改科目」（`這三筆毛巾都記在 居住費`）如果要做得夠聰明，會需要判斷
「這三筆」指的是哪三筆。但我認為**用 DB 最後 N 筆就夠**，仍然不需要 AI。
真正需要 AI 的只有 A‑1 一個。

## 附錄 B　怎麼列出 telegram 頻道裡的內容

（妳中途問的，也是 `.tap` 將來要拿來做「從 telegram 聊天整理需求規格書」的基礎。）

### B‑1　先講不能用的路

| 指令 | 結果 |
|---|---|
| `openclaw session search …` | **沒有這個指令**。只有 `openclaw sessions`（list / tail / compact / cleanup / export-trajectory） |
| `openclaw message read --channel telegram --target -100XXXXXXXXXX` | `GatewayClientRequestError: Unsupported Telegram action: read` |
| `openclaw message search` | help 寫明是 **Search Discord messages**，telegram 不支援 |

Telegram Bot API 本來就不給 bot 讀歷史訊息，所以這條路是死的。

### B‑2　能用的路：讀 gateway 寫在本機的三份紀錄

都在 `~/.openclaw/agents/<agentId>/`：

| 來源 | 路徑 | 有什麼 | 缺什麼 |
|---|---|---|---|
| **trajectory** | `sessions/<sid>.trajectory.jsonl`，取 `type: "prompt.submitted"` | `data.prompt` 內含 ①`Conversation info` metadata（有 `message_id`、`sender`、`timestamp`）②`Conversation context` 前幾則，格式 `#id 時間 GMT+8 名字: 內容` ③本次新訊息。**唯一能拿到 telegram message id 的來源**，而且 ② 連「沒觸發 agent 的鄰近訊息」都撈得到 | 只保留還沒被輪替掉的 session |
| **transcript** | `sessions/<sid>.jsonl` 與 `.jsonl.reset.*` | 乾淨的 `role:"user"` 原文，含 `sourceChannel`／`senderName`／`content`，多行訊息保留換行 | 沒有 message id |
| **codex rollout** | `agent/codex-home/sessions/YYYY/MM/DD/rollout-*.jsonl` | runtime 另一份副本，可補 trajectory 已輪替掉的部分 | 同樣會被清 |

對照關係要靠 `sessionKey`：格式是 `agent:<agentId>:<channel>:<group|channel>:<rawId>`，
本頻道是 `agent:appliance:telegram:group:-100XXXXXXXXXX`。
`openclaw sessions list --all-agents --json` 可以列出目前所有 key 與對應檔案。

### B‑3　現成工具

我把合併三來源的邏輯寫成 `genesis/tools/dump-channel.js`（純 node，無相依）：

```bash
node genesis/tools/dump-channel.js --tap genesis/.tap --user-only --format txt
node genesis/tools/dump-channel.js --tap genesis/.tap --format md   > channel.md
node genesis/tools/dump-channel.js --channel telegram --target -100XXXXXXXXXX --format json
```

`--tap` 直接吃 `.tap` 檔；也可以 `--channel` / `--target` 手動指定。
target 會正規化，所以 discord 的 `channel:123` 和 `discord:channel:123` 都通。
stderr 會印一行 coverage：

```json
{"recovered":163,"idRange":[5,242],"missingIds":[9,12,16,…],"firstTs":"2026-07-17 23:47:31"}
```

### B‑4　這次的缺漏，以及為什麼不影響結論

242 則裡還原 163 則，缺 75 則。大段缺口有三處，成因不同：

不過缺口可以用帳本反推。那幾段期間帳本新增的是：


**全部都是 `{item}{number}` 或 `提款{number}`**，沒有任何新格式。
所以第一章的格式清單可以視為完整。

### B‑5　⚠️ 給「.tap → 需求規格書」計畫的重要提醒

DESIGN.md §5 第一條：**被 interceptor 攔掉的訊息不會寫進 session transcript**。

也就是說——**這套撈法只對「還沒被攔截」的頻道有效**。一旦 openclaw-bookkeeper
上線開始攔記帳訊息，那些訊息就從此不會出現在 trajectory 或 transcript 裡，
未來再跑 `dump-channel.js` 只會撈到漏給 AI 的那些自然語言。

所以如果妳希望 `.tap` 頻道的完整對話長期可回溯（不管是為了做需求規格書，
還是為了觀察哪些輸入詞退回給 AI），**script 這一側必須自己留一份 log**：
收到的 `body` 原樣、判給哪個格式、handled 還是 exit 20。
這份 log 順便就是白名單與 `item_category` 快取的訓練資料來源，
建議階段二一起設計進去。

# 階段一定案

依 `FEEDBACK1.md` 與後續討論收斂。**階段二以本節為準**，前面章節是推導過程。

## 0　總原則：固化，不是產品

這是自用工具，不是要發佈的軟體。關鍵字、預設科目、贅詞白名單**一律寫死在程式裡**，
不進 `openclaw.json`，也不提供聊天內的維護語法。改一行陣列 ＋ 重啟 gateway
是幾分鐘的事，不必為了避免「改版」去蓋 config 管線。

推論：設計重點是**「弄錯時看得出來」**而不是「不可能弄錯」。
力氣花在確認訊息與 debug log。

唯一的例外是 `item_map`（見 §3）——那不是規則，是跑出來的資料。

## 1　輸出格式

`[<日期時間> ]#<id> <科目> (<品項>) <金額> 餘額 <餘額>`

沿用舊 spec 的間距與用字（科目與括號之間有空格、寫「餘額」不寫「餘」），
只在最前面（有日期時間時則在其後）插 `#<id>`：

```text
#358 雜費 (毛巾) 80 餘額 3328
#359 雜費 (油漆刷) 25 餘額 3303
```

其餘動作比照插入（階段二確認細節）：

```text
#364 入金 (酬勞) 10000 餘額 12000
#358 居住費 (毛巾) 80 -> 120 餘額 3328 -> 3288

```

`id` 直接用 `entries.id`（`AUTOINCREMENT`，刪除不重用，archive 後**不重置**）。

**報表顯示 ID**：`detail`、`category-detail`、`expand` 要（那正是要挑一筆來改的場合）；
`report`（科目加總）不要，沒有單筆可指。

## 2　以 ID 更正

```text
{id}...  {科目}         → 改科目     358 居住費        358 359 360 居住費
{id}...  名稱 {值}       → 改品項名   424 名稱 巷口饅頭
{id}...  金額 {值}       → 改金額     358 金額 80       358 359 金額 80
{id}...  刪除           → 刪除       286 刪除
刪除 {id}...            → 刪除       刪除 286
```

辨識規則：**從頭連續的純數字 token = ID 清單**；其後第一個 token 若是欄位詞
（`名稱` / `金額` / `刪除`）就照欄位詞，否則命中 `categories` 表就是改科目。
與 `{item}{number}` 不衝突，因為記帳的 item 一定含非數字字元。

金額**不能裸打**（`358 80` 看起來就像 `{item}{number}` 的記帳），必須用欄位詞。

**裸值沒命中科目表時**：先算與現有科目的編輯距離，≤1 就回問，不改任何東西；
完全不像任何科目才當成改品項名。

```text
424 巷口饅頭
→ #424 外食費 (巷口饅頭) 34 餘額 3303

423 居住廢
→ 「居住廢」不是現有科目，你是不是要指「居住費」？
   若要改品項名請打：423 名稱 居住廢
```

這一組語法讓舊 spec 的**兩階段 rowid 流程整個廢除**，也讓附錄 A‑4 的
「最後 N 筆」猜測性設計取消。

## 3　`item_map`：kind 與科目的學習型快取

```sql
item_map(note_key TEXT PRIMARY KEY, kind TEXT, category TEXT, updated_at TEXT)
--  提款  | in  | NULL
--  毛巾  | out | 居住費
```

AI 判斷函數（**全 script 唯一的 AI 呼叫點**）：

```
classify(note, categories) -> { kind: "in" | "out", category: string | null }
```

`kind` 一定要問，不能只問科目。寫死的入金關鍵字清單是**快路徑**；
清單漏詞時（`匯款5000`）若不問 kind，會被默默記成支出、餘額往反方向跑，
而且沒有徵兆。多問一個欄位就把「記反」降級成「問一次」。

- **比對方式**：全半形正規化＋去空白後**精確相等**，不做模糊或子字串。
  所以 `提款手續費` 天生不會命中 `提款`，舊 spec 的手續費特例規則可以刪掉。
- **唯一的例外**：精確 miss 時，試「是否以某個 `kind=in` 的 key 結尾」，
  讓 `某銀行提款` 命中 `提款`。科目那側**不做**任何模糊比對。
- **查快取時先驗證科目仍在 `categories` 表**，不在就當 miss 並清掉孤兒。
- `category` 為 `null`（AI 判不出來）→ `exit 20` 交給 AI 問使用者，**不要塞雜費**。

寫入時機三個，都不額外呼叫 AI：AI 判過後寫、使用者明講科目時寫
（`維他命飲67 外食費`，最可靠的訓練資料）、ID 更正時覆寫。

### 矛盾處理

1. **後寫的贏**（last-write-wins），不問。
2. **不追溯**。以前記成雜費的毛巾維持雜費；追溯會讓已對過帳的月份報表變動。
   真要改歷史是另一個動作，低頻，交給 AI。
3. **覆寫既有快取時多印一行**，新建不印：

```text
#358 居住費 (毛巾) 80 餘額 3328
往後「毛巾」預設記為 居住費（原為 雜費）
```

## 4　餘額查詢

整句 trim 後**含「餘額」、不含數字、長度 ≤6** → `balance`，否則 `exit 20`。
`餘額`、`餘額多少`、`顯示餘額`、`餘額?` 都過；
`剛剛餘額 1263，扣完 60 怎麼會是 1023` 不會被誤判成查餘額。

## 5　log 是 debug 行為

| | 開關 | 寫哪 |
|---|---|---|
| `item_map` 快取寫入 | **永遠開**，這是營運行為 | `book.db` |
| 原始 body、判給哪個格式、handled / exit 20 | 跟 debug 對齊，可關 | log 檔 |

快取是即時寫 DB，不經過 log；關掉 log 不影響記帳正確性。
log 純粹給開發者看「哪些輸入退回給 AI」，用來決定白名單補什麼。
建議 script 讀自己的 `BOOKKEEPING_DEBUG`（由 route 的 `env` 給），
不跟 plugin 的 `debug: true` 共用——後者每一輪都寫 trace，混在一起難讀。

## 6　其餘自行決定的細項

- **倒推標記**涵蓋 `後` / `完` ＋ 可選的 `剩`：`買菜後3229`、`買菜完1263`、
  `買菜後剩 10250` 走同一支 parser。
- **語音／影片訊息**一律 `exit 20`（`cleanedBody` 拿不到轉錄文字）。
- **贅詞白名單**寫死；缺詞的代價只是那句話 `exit 20` 花 token，結果仍正確，
  所以可以慢慢長。這跟入金關鍵字的不對稱性見 §3。

## 7　還沒定、階段二要決定的

  做得到，但屬於一次性低頻動作，要看值不值得佔語法面積。
