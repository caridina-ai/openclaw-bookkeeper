## 病灶一：`{編號} 時間 {日期時間}` 這個格式根本不存在

`parse_by_id` 認得 `名稱`／`品項`／`金額` 三個欄位關鍵字，認不得 `時間`，
於是掉進最後那條「剩下的字就是新品項名」的預設路徑。

**這是四筆裡最嚴重的一種，因為它 exit 0，log 寫的是 `handled`。**
從 log 那一邊看一切正常，只有讀 .tap、看到使用者下一句在抱怨才知道出事。

而且底層根本改不動時間：`book.py edit` 只有 `--to`／`--category`／`--note`，
`--date` 是**搜尋條件**不是新值。所以連 AI 接手都改不動——當天 AI 是自己
下 SQL 去改的，還失敗了兩次（telegram 上兩則 `⚠️ Bash failed`）。

殃及快取：`cmd_edit` 的 `--note` 分支會 `record_item`，所以認錯格式不只
寫錯一筆帳，還把 `時間 8/9 12:09 → 買菜金` 學進了 `item_map`，污染往後的判斷。

## 病灶二：問模型判科目，一次不成就整則放棄

兩筆漏接的共同點是「訊息裡有沒學過的品項」。把原文用暫存帳本重放，
**兩筆都一次就成功**——parser 沒問題，是當下那次 `openclaw infer model run`
失敗了。當天 telegram 上有好幾則 `Model Fallback … usage limit`，
暫時性失敗有跡可循。

從時間差也看得出來不是逾時（subprocess 上限 45 秒）：

- 14:38:12 送出 → 14:38:26 寫 log，約 14 秒
- 15:00:57 送出 → 15:01:22 寫 log，約 25 秒

代價被放大的是多行那筆：四行裡只有「牙間刷」是新品項，一個未知品項的
分類失敗，拖著另外三行已經學過的毛巾一起交給 AI。AI 接手後把牙間刷記成
居住費，使用者還得再打一次 `75 保健費` 更正。

`孝親費 1000`、`奉獻250` 這種，品項就是科目名，卻還是跑去問了模型。

## 查案時卡住的地方

`why` 沒有記。log 只寫 `pass`，分不出「格式沒認得」還是「問模型當掉」，
而這兩件事的修法完全相反——前者要改 parser，後者改 parser 是白改。
這次是靠「把原文重放一次看會不會成功」才分開的，下次應該讓 log 自己講。

三種病灶的特徵長這樣，值得記住：

```
log: result=pass, why=unparsed        使用者講了 parser 不認得的話。
                                      補格式是省 token；不補也不會錯。

log: result=pass, why=classify:*      parser 沒問題，是問模型那步出事。

log: result=handled，但下一則使用者在抱怨
                                      最嚴重：接到了，然後做錯事。
                                      log 這邊看起來完全正常。
```
